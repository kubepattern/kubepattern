# Offline replay of the evaluation scenarios

The replay re-runs the correctness experiments of the evaluation without minikube: a real `kube-apiserver` and `etcd` (pinned to `KUBERNETES_VERSION` of `../env/versions.env`) on localhost, with the CRDs of the nine platforms at their pinned versions and **no controllers**. It needs no container runtime, only outbound HTTPS to `dl.k8s.io` and GitHub, and runs in about two minutes. It was built to validate the engine update that resolves the DSL limitations (`../results/limits/`), in an environment where minikube was not available.

## What it reproduces, and what it does not
| Reproduced | Not reproduced (use the minikube scripts) |
|---|---|
| RQ2 effectiveness on the 9-platform scenarios (`../scenarios/`), scored with `../scripts/score.py` | anything that needs running controllers or time: RQ3 (platform signals), RQ5 (CronJob timeline), RQ8 (`spec.for`) |
| RQ2b mutation testing (`../scripts/mutate.sh` with replay hooks) | cost and footprint (RQ4 audit, RQ6c), Kyverno (RQ6) |
| the controlled cases of the Krateo case study (seeded namespaces `kp-krateo-a/b`) | the natural state of the Krateo case study (Krateo install, portal, compositions) |

**Fidelity check.** On the replay, the engine of `dev` before the update (`a848c98`) with the original Patterns gives exactly the minikube results: 46 Smells, 43/52 with P = R = 1.00, 10/10 probes as predicted, 0 unlisted, mutation 15/15; on the Krateo controlled cases, 29 TP, 39 TN and 14/14 probes as predicted.

**Controller shim.** Objects that controllers or installers create on minikube are created explicitly, each with the controller it stands in for (`scenario.sh`, `krateo.sh`, `mutate-shim.sh`): the `argocd` and Kargo project namespaces, the Applications generated by three ApplicationSets (owned by them), one CertificateRequest per Certificate revision (owned, with the rotation of Certificate `api`), the KubeVela Application `a3`, the status of the seeded Krateo CompositionDefinitions and the Panel rendered by a Krateo composition; garbage collection and the ApplicationSet controller in the mutation step. The CNPG self-referencing Pooler is not created, because the CNPG webhook rejects it on minikube. CRDs keep their schemas, minus conversion webhooks; Krateo's CRDs are generated without schema (only the objects matter to the engine).

## Usage
```bash
cd evaluation/replay
./up.sh            # etcd + kube-apiserver on 127.0.0.1:6443; kubeconfig in .state/
./crds.sh          # CRDs of the 9 platforms (pinned) + KubePattern's CRDs
./scenario.sh      # RQ2 scenarios + controller shim
./krateo.sh        # Krateo controlled cases (optional)
./regression.sh    # full suite -> ../results/limits/ (builds the baseline engine from KP_BASE)
./down.sh --purge  # stop and delete the state
```
Single runs: `./run.sh <engine binary> <label> <pattern dirs or files>...` replaces the installed Patterns (later files override earlier ones with the same name), deletes every Smell, runs the engine once and writes `.state/runs/<label>/smells.json`. Score it with `../scripts/score.py` (RQ2; `--probe-expect truth` for Patterns that resolve the probes) or `./score-krateo.py` (Krateo controlled cases; `--with-kyverno-only` adds the smell that had only a Kyverno policy). Mutation testing: `REPLAY_ENGINE=<bin> REPLAY_PATTERNS="<dirs>" ./mutate.sh <label> <out dir>`.

Scripts source `env.sh`, which exports `KUBECONFIG=.state/kubeconfig`: they never touch the minikube profiles.
